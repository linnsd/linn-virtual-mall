## Findings

- [High] Stored XSS through visitor statistics — `index.html:4777`, `index.html:4781`, `index.html:4786`; `supabase/001_initial.sql:42`.
  Evidence: visitors can insert/update their own `mall_visits.data`; the SQL constraint checks JSON object/size, not numeric metric types. The Admin renderer adds untrusted `coupons`, `draws`, `drives`, `flights`, `sits` and corner/prize values to aggregates and interpolates the results into `innerHTML` without escaping. Extracting and running the actual renderer with a mocked visitor row containing a harmless HTML marker confirmed that the marker appears unescaped in the resulting HTML.
  Risk: an anonymous authenticated visitor can persist executable markup; opening Admin stats could execute it with the administrator's origin/session privileges. No browser payload or live database write was performed during this audit.
  Recommended mitigation: strictly validate/normalize numeric metric values before aggregating; render numbers through DOM text or escaped output; constrain accepted data types in the database. Add a regression test for the actual rendering path with hostile numeric fields and dictionary values.

- [Medium] Daily coupon state remains on the previous day in a long-running tab — `index.html:4499`, `index.html:2837`, `index.html:4516`; `supabase/004_member_coupons.sql:4`.
  Evidence: `TODAY` is a constant evaluated once, and collected mesh visibility / `couponGot` are loaded only on startup. Database inserts use the server's current UTC day. The frame loop never detects a day change or reloads the member collection.
  Risk: after UTC midnight (06:30 Asia/Yangon), yesterday's coupons remain hidden, the HUD can describe the wrong day and subsequent inserts/reward messages can disagree on their day until reload.
  Recommended mitigation: use a current-day collection controller; refresh on date change and tab visibility restoration; guard in-flight collections so a response from the previous day cannot populate the new day's state. Keep analytics and lucky-draw daily state consistent too.

- [Medium] AI spending limits are local to one serverless instance — `api/ask.js:4`, `api/ask.js:8`, `api/ask.js:13`.
  Evidence: the endpoint accepts requests without an Origin header or session and calls the paid provider; rate history lives only in a module-level Map. A local test with stubbed fetch confirmed an unauthenticated/no-Origin request invokes the upstream path. No external AI call was made.
  Risk: separate instances/restarts do not share quotas; Origin checks do not authorize non-browser clients. Sustained traffic can exceed an intended global budget. Guest access can remain available while still enforcing quotas.
  Recommended mitigation: add shared rate limiting plus a global spend/request cap; optionally use the existing verified guest/member identity as one quota dimension. Add timeouts to upstream calls. Do not rely on Origin or the prompt phrase as authentication. The current source already labels its limiter best-effort.

- [Medium] Malformed message elements bypass controlled API error handling — `api/ask.js:20`.
  Evidence: `messages: [null]` throws `TypeError: Cannot read properties of null (reading 'role')` before the handler's try/catch. Reproduced locally with a placeholder API key and stubbed fetch.
  Risk: malformed public requests cause unhandled errors rather than the intended 400 response and can consume server/error-log resources. Existing tests do not cover this endpoint.
  Recommended mitigation: validate every message is a non-null object with an allowed role and string content before mapping; return a controlled 400 and add malformed-input regression tests.

## Open Questions / Missing Product Flows
- Email/password login has no forgot-password/reset flow or resend-confirmation action (`index.html:2739`). These are useful additions for members who cannot return to their account; they are feature gaps rather than a regression against the original request.
- Coupons remain explicitly demo-only. The RPC validates identity and a known ID, but not trusted movement/proximity (`supabase/004_member_coupons.sql:17`). Before real discounts, add a trusted claim/reward policy, issued/used/expired states and server-side redemption checks. This is a documented limitation, not a newly discovered privilege bypass.
- Live Google provider settings, consent/callback, production email delivery and real-account metadata persistence still need end-to-end verification. This review did not access provider credentials or change external settings.
